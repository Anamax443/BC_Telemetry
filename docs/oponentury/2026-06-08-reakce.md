### Bod #1 — accept-s-výhradou
Pro **AppPageViews** přijímám whitelist `clientType == "Web"` (dashboard čte pageViews). Pro **AppTraces**
ale upozorňuji: traces nesou i **error eventy RT0031 (Authorization Failed)**, které workflow §12 explicitně
potřebuje pro monitoring migrace SUPER→role. Striktní `== "Web"` je u traces OK (RT0031 z web session má
clientType Web), ale je třeba to ověřit na reálných datech — pokud by se RT0031 logoval pod jiným clientType,
whitelist by je zahodil. **Zapracováno:** dokumentace i BUILD používají `== "Web"` pro obě tabulky + poznámka
k ověření RT0031. Pozn.: pageViews ingest filtr v KQL je `== "Web"` tak jako tak.

### Bod #9 — accept-s-výhradou (částečný reject návrhu read-only setu)
Bezpečnostní obavu **přijímám**, ale navržené řešení (read-only Permission Set TELEMETRY: Read+Execute, žádný
Write) **metodicky nefunguje**: smyslem sledovacího období je, aby uživatel **normálně pracoval** pod plným
přístupem a telemetrie zachytila reálné použití. Read-only set by mu zablokoval zápisové operace → nemohl by
dělat svou práci → telemetrie by byla zkreslená. Navíc by generoval RT0031 už během sledování, což maskuje
signál pro fázi nasazení rolí.

**Místo toho:** riziko se řeší **time-boxem** (3 měsíce, pak odebrat plný přístup), úzkým okruhem sledovaných
účtů a monitoringem. Volitelně lze plný přístup zúžit vyřazením nejcitlivějších admin objektů (Permission/User
setup), ale ne na čisté čtení. Zapracováno jako poznámka v [dokumentace.md §12](../dokumentace.md) a workflow §8 v BUILD.
