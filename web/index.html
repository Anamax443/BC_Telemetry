🗑 Smazat audit záznamy

Nevratně smaže naimportované záznamy Auditu změn (dbo.BCChangeLog) u zaškrtnutých firem — užitečné pro úklid bobtnající DB. Mazání proběhne přes denní úlohu (pár minut). Pozor: pokud firma zůstává sledovaná (zaškrtnutá výše), začnou se její záznamy při příštím importu natahovat znovu od nejstarších — pro trvalé odstranění ji nahoře odškrtni a ulož (nebo zapni automatické mazání a odškrtni ji).

Spojení s Business Central

Ověření, že jsme reálně napojení na BC tenant — ne jen že běží služba. Zdrojem je poslední skutečné volání BC API: importní skript při každém běhu zapíše výsledek (přihlášení service principalem + zkušební dotaz) do ops/bc-status.json. Hlavička ukazuje zeleně, dokud je toto ověření čerstvé; po 26 h bez úspěšného kontaktu zežloutne (vynechaný noční běh) a při chybě zčervená s důvodem. Ověřit teď vyžádá nový živý test — provede ho servisní účet, protože secret service principalu je v jeho Credential Manageru, ne u web služby.

Ruční obnova dat

Vynutí okamžitý běh importu (3 moduly z Azure / BC) + snapshot. Jinak běží automaticky denně 02:00 (úloha BC_Telemetry_Daily).

Zobrazení tabulek

Výchozí počet řádků na stránku v tabulkách (Aktivita, Audit, Databáze…). Uloženo v prohlížeči; v každé tabulce lze přepnout i přes stránkovač dole.

Správa služby a úloh

Stav naplánovaných úloh, zastavení běžícího (i zaseknutého) importu a restart web služby (nasadí změny server.js — služba se sama nahodí přes NSSM).

Retenční politika

Jak dlouho se drží data; projeví se při dalším běhu importu. Raw page log (modul A) i Change Log (modul B) se po této době mažou, agregáty kumulují navždy.

načítám…

Počet řádků ve snapshotu

Kolik řádků na sekci (Audit změn / Aktivita / RT0031) snapshot stáhne ze SQL do data.json. Filtruje se vždy jen v tomto stropu. Default 5000; vyšší = hlubší historie pro filtrování, ale větší data.json (přes ~100 000 řádků pomalejší načtení v prohlížeči; timeout dotazu zvednut na 15 min). Projeví se po nejbližší ↻ obnově (⚙ Nastavení → Ruční obnova nebo tlačítko ↻ v hlavičce).

načítám…

E-mailové notifikace

Stav a alerty e-mailem přes M365 Direct Send (odesílá noční úloha jako služba). Příjemci i odesílatel musí být @axima.cz. Alerty: selhání importu, zastaralý modul (nejnovější záznam starší než N h), expirace SP secretu. Synchronizace ukazuje ~5 % záměrně (cloud drží vše, lokál jen výřez) — proto se hlídá čerstvost, ne total %.

Plán importu (okno + četnost)

Kdy a jak často běží úloha BC_Telemetry_Daily. Interval 0 = jednou denně v čase Od. Jinak se opakuje každých N minut v okně Od–Do (rychlejší dosync/backfill — víc běhů za noc). Projeví se ihned.

Síťový whitelist

Formální omezení zobrazení této stránky na vymezené IP adresy / rozsahy. Zdroj pravdy je Windows Firewall rule BC Telemetry Dashboard (8080). Jedna IP nebo CIDR na řádek (např. 10.8.2.0/24).

Údržba logů

Denní importní logy se po každém běhu automaticky mažou po 30 dnech (wrapper). Logy služby (web.out/err.log) rotuje NSSM při 5 MB. Ruční čištění není potřeba.

BC Telemetrie — dokumentace

Příručka pro práci s dashboardem. Dashboard ukazuje, kdo co v Business Centralu reálně používá, kdo co vytvořil, změnil nebo smazal a komu po zúžení práv chybí oprávnění — slouží jako podklad pro nastavení oprávnění (permission setů) na míru místo plošného SUPER.

1 · Orientace na stránce

  • Hlavička — název vlevo (klik = zpět na úvod), indikátor spojení s BC (zelená = jsme napojení na tenant a ověření je čerstvé; najetím myší uvidíš podrobnosti), živý čas (tiká jako kontrola, že stránka žije; když stojí, stránka zamrzla → Ctrl+F5), stáří dat (jak dávno proběhl poslední import), přepínač jazyka CS/EN a přepínač 🌙 / ☀ světlý/tmavý režim.
  • KPI dlaždice — souhrnná čísla (aktivní uživatelé za 30 dní, použité stránky, otevření, RT0031 chyby). Jsou klikací — kliknutím skočíš na odpovídající záložku.
  • Pruh pod KPI (synchronizace) — kolik záznamů je v cloudu vs. staženo do databáze (per modul) + velikost lokální DB.
  • 📊 Manažerská zpráva (vpravo nahoře) — otevře přehledovou zprávu s grafy, kumulacemi a žebříčky (top uživatelé/stránky/firmy, trend, audit), kterou lze vytisknout / uložit jako PDF nebo HTML.

2 · Záložky — co kde najdeš

Aktivita uživatelů

Kdo otevírá které stránky BC a jak často. Základ pro návrh rolí — vidíš reálné využití. Filtruj podle uživatele/firmy, seřaď podle „Otevření", exportuj.

👤 Uživatelé

Telemetrie zná uživatele jen jako pseudonymní GUID. Tady k němu přiřadíš reálné jméno (podle firem/stránek v nápovědě); jméno se pak ukáže všude. Vyplň pole „Reálné jméno" → Uložit jména.

Audit změn

Kdo kdy co vytvořil/změnil/smazal — s reálným jménem, firmou, tabulkou/polem a starou→novou hodnotou. Filtr Firma a Akce = rozbalovací, datum jako rozmezí od–do.

Permission errors (RT0031)

Komu chybí oprávnění. Hlídej ho hlavně první 2 týdny po zúžení práv — doplníš podle něj chybějící přístupy.

Trend

Vývoj otevření a aktivních uživatelů v čase, lze přepnout na konkrétní firmu (graf + tabulka).

🗄 Databáze

Stav SQL serveru, velikost databáze a seznam tabulek s počty řádků — provozní přehled.

🖥 Terminál

Živá aktivita služby a log posledního importu (auto-obnova 10 s) — když chceš vidět, co systém právě dělá.

⚙ Nastavení auditu

Výběr firem, u kterých se sleduje Audit změn (vypni obří firmy), a mazání naimportovaných audit záznamů.

⚙ Nastavení

Spojení s BC, ruční obnova dat, retenční politika, plán importu, síťový whitelist, restart služby, údržba logů.

3 · Hlavní úkol: sestavení oprávnění na míru

Postup, jak z dat dashboardu vytvořit permission set per uživatel/roli místo plošného SUPER:

  1. Sběr dat — uživatel jede pod plným přístupem, data se kumulují (ideálně ~3 měsíce).
  2. Namapuj jména — záložka 👤 Uživatelé → ke GUID doplň reálná jména a ulož.
  3. Zúžení výběru — záložka Aktivita uživatelů → vyfiltruj uživatele / firmu, seřaď podle „Otevření".
  4. Export — ⬇ Export ▾ → vyber formát CSV / TXT / HTML / PDF (CSV se otevře v Excelu, oddělovač ;, s reálnými jmény). Exportuje se celá filtrovaná sada, ne jen zobrazená stránka.
  5. Analýza — v Excelu kontingenční tabulka (řádky = Page ID/Stránka, filtr = uživatel) → seznam objektů, kam uživatel reálně chodí.
  6. Nasazení — z toho sestav permission set v BC, odeber plný přístup.
  7. Kontrola — sleduj záložku Permission errors (RT0031) a doplň, co chybí.

Telemetrie využití (Aktivita) má jen pseudonym → proto je krok 2 (namapování jmen) klíčový. Audit změn má reálné jméno nativně.

4 · Práce s tabulkami

  • Hledání — pole nahoře filtruje přes všechny sloupce („obsahuje").
  • Per-sloupcové filtry — řádek pod hlavičkou: Firma/Akce = rozbalovací seznam, text = „obsahuje", datum = rozmezí od–do. „Vyčistit" zruší vše.
  • Řazení — klik na hlavičku sloupce (druhý klik obrátí směr).
  • Stránkování — dole « ‹ strana X/Y › » + přepínač 50 / 100 / 200 / 500 / vše. Výchozí počet řádků nastavíš v ⚙ Nastavení (uloží se v prohlížeči).
  • ⬇ Export ▾ — stáhne aktuálně filtrované a seřazené řádky ve formátu CSV (Excel, oddělovač ;), TXT (tab), HTML (samostatná tabulka) nebo PDF (přes tisk).

5 · Provozní úkony (⚙ Nastavení)

  • Spojení s Business Central — ukazuje, jestli jsme reálně napojení na tenant, kdy se to naposledy prokázalo, a umí si vyžádat nové živé ověření.
  • Ruční obnova dat — vynutí okamžitý import + snapshot (jinak běží automaticky dle plánu).
  • Plán importu — okno „Od–Do", četnost (á N minut) a dny v týdnu.
  • Retenční politika — kolik měsíců/dní se data drží.
  • Síťový whitelist — které IP adresy smí dashboard zobrazit (jedna IP / CIDR / rozsah).
  • Restartovat službu — bezpečný self-service restart (po nasazení změn serveru).

6 · Tipy & řešení potíží

  • Dashboard se nenačte / „web není dostupný" (timeout) — nejčastěji firewall na serveru (pravidlo dashboardu neplatí na aktuálním síťovém profilu po rebootu). Řeší správce na serveru; běžnému uživateli pomůže Ctrl+F5 až po obnově.
  • Indikátor BC je žlutý nebo červený — žlutá znamená, že se s tenantem nepodařilo prokazatelně spojit déle než 26 hodin (typicky vynechaný noční běh), červená že poslední pokus selhal a v nápovědě je důvod (vypršelý secret, chybějící souhlas, odebraná práva).
  • Data vypadají stará — zkontroluj „stáří dat" v hlavičce; ruční obnovu spustíš v ⚙ Nastavení → Ruční obnova.
  • Živý čas stojí — stránka zamrzla, obnov Ctrl+F5.
  • Tmavý / světlý režim — přepínač 🌙/☀ v hlavičce (volba se pamatuje).
  • Jazyk — přepínač CS/EN v hlavičce; přepne i tuhle dokumentaci a volba se pamatuje.
  • Tisk / PDF — tlačítko 🖨 nahoře v této záložce; vytiskne právě zobrazenou příručku vždy bíle. V dialogu zvol cíl „Uložit jako PDF".

1 · Přehled — k čemu to je

Nad Microsoft Dynamics 365 Business Central (Cloud / SaaS) staví systém, který odpovídá na tři otázky, na něž BC SaaS sám přímou odpověď nedá:

Modul A

Co uživatelé reálně používají

Telemetrie využití stránek → podklad pro permission set mining (seškrtat oprávnění na to, co je opravdu potřeba, místo plošného SUPER).

Modul B

Kdo co vytvořil / změnil / smazal

Audit změn z BC Change Logu s reálným jménem uživatele (kdo, kdy, jaká tabulka/pole, stará→nová hodnota).

Modul C

Komu po zúžení práv chybí oprávnění

Permission errors RT0031 z telemetrie — hlídá, kde uživateli po nasazení rolí chybí přístup.

Architektura záměrně stojí na free tieru (Application Insights 5 GB/měs zdarma) + on-prem SQL + lehkém Node dashboardu → provoz prakticky zdarma a data zůstávají v doméně.

2 · Architektura — tok dat

BC Cloud ──telemetrie──▶ Azure Application Insights / Log Analytics │ (Service Principal, neinteraktivně) ┌─────────────────────┼─────────────────────┐ modul A modul C modul B (BC Change Log → OData) (AppPageViews) (AppTraces) └─────────────────────┼─────────────────────┘ ▼ SQL (raw → inkrementální rollup → agregáty) ← servisní účet, přes denní úlohu ▼ data.json ──▶ Node služba (dashboard + IP whitelist) ← web NEsahá na SQL/BC

Dvě oddělené identity podle principu nejmenších oprávnění:

  • Web služba BC_Telemetry_Web (Node + NSSM, běží jako LocalSystem) — servíruje dashboard a nesahá přímo na SQL ani BC. Požadavky z UI (import, mazání, plán…) zapisuje jako soubory do ops/ fronty.
  • Servisní účet AXINETWORK\svc-bc-telemetry — pod ním běží denní úloha BC_Telemetry_Daily (wrapper), která jako jediná přistupuje na SQL a BC OData a zpracovává ops frontu.

Z tohoto rozdělení plyne i to, proč kontrolu spojení s BC provádí servisní účet a ne web: secret service principalu leží v Credential Manageru servisního účtu, kam LocalSystem nevidí.

3 · Registrace u Microsoftu (Azure + Entra)

Pro neinteraktivní (server-to-server) čtení telemetrie i BC API slouží jedna aplikace v Microsoft Entra ID — App registration BC_Telemetry_SP (Service Principal).

3.1 Azure subscription + Application Insights (moduly A/C)

  1. Azure Portal → Předplatná → Pay-as-you-go (App Insights jede ve free tieru = $0; karta jen kvůli identitě).
  2. Resource Group rg-bc-telemetry, region West Europe.
  3. Application Insights appinsights-bc-production, Resource Mode: Workspace-based (vytvoří se Log Analytics workspace).
  4. Workspace → Usage and estimated costs → Data Retention 31 dní + Daily cap 0,5 GB/den (pojistka nákladů).
  5. Workspace → Overview → zkopíruj Workspace ID (do importních skriptů A/C).
  6. App Insights → Overview → zkopíruj Connection String (vloží se v BC, viz §4).

3.2 Entra App registration (Service Principal)

  1. Entra → App registrations → New registration → BC_Telemetry_SP, Single tenant → Register.
  2. Zkopíruj Application (client) ID (NE „Object ID" — to je něco jiného).
  3. Certificates & secrets → New client secret → zkopíruj Value (ukáže se jen jednou).

⚠ Past: secret je Value (~40 znaků, mzm8Q~…), NE Secret ID (36-znakový GUID) — záměna → token request vrací 401. Secret se nikam nepíše, leží v Credential Manageru servisního účtu (targety BC_Telemetry_SP a BC_Telemetry_BCAPI). Aktuální expirace 2028-06-07 — sledovat.

3.3 Zmocnění pro App Insights (moduly A/C)

Log Analytics workspace → Access control (IAM) → Add role assignment → Log Analytics Reader → member BC_Telemetry_SP → Review + assign. Tím SP smí číst AppPageViews / AppTraces přes KQL.

3.4 Zmocnění pro BC API (modul B, S2S) — tři pasti

  1. Redirect URI — App registration → Authentication → Add a platform → Web → https://businesscentral.dynamics.com/OAuthLanding.htm (Implicit grant NEzaškrtávat).
    Bez něj spadne „Udělit souhlas" v BC na AADSTS500113.
  2. API permission + admin consent — API permissions → Add → APIs my organization uses → Dynamics 365 Business Central → Application permissions → API.ReadWrite.All → Add → Grant admin consent (musí být zelené Granted).
    Bez něj má token prázdné roles → 401 i s BC sadami.
  3. Registrace app usera přímo v BC — viz §4.3.

4 · Registrace v Business Centralu

4.1 Zapnout telemetrii

BC Admin Center (…/<tenant>/admin) → Environments → Production → Telemetry → Define → vlož Connection String z App Insights → Save. V aktuální verzi BC bez restartu prostředí; data tečou do ~5 min při reálné aktivitě uživatelů (Desktop / WebClient).

4.2 Change Log + web service (modul B)

  1. Change Log Setup → Change Log Activated = ON.
  2. Tables → pro citlivé tabulky zapni Log Insertion / Modification / Deletion (např. Access Control 2000000053, User 2000000120, doklady, položky). Neloguje zpětně.
  3. Web Services → New → Type Page, Object ID 405, Service Name ChangelogEntry, Published.

⚠ Microsoft postupně ruší publikování UI stránek jako web service → durable varianta = vlastní AL API page (plánováno). Přechod na standardní /api/v2.0 řešení není — Change Log Entry ani BC Users tam jako entity neexistují (viz docs/bc-api-integrace-standard.md).

4.3 App user pro Service Principal (S2S)

  1. BC web klient → vyhledej „Aplikace Microsoft Entra" (Page 9861) → New.
  2. Client ID = Application (client) ID z §3.2 + popis.
  3. Sady oprávnění → přidej D365 BUS PREMIUM (nebo vlastní read sadu).
  4. Společnost nech prázdné = platí pro všechny firmy.
  5. Stav → Povolený → Udělit souhlas (přihlaš se jako admin) → naplní se ID uživatele. OData pak čte všech 12 firem.

⚠ SUPER ani SUPER (DATA) NELZE app userovi přiřadit — BC je odmítne. Použij D365 sady nebo custom read.

5 · Tři moduly — co čtou

A · Využití stránek

Log Analytics → AppPageViews

Identita = UserId = pseudonymní GUID (NE AAD object id; Microsoft ho nerozkrývá). BC dimenze v Properties.* (alObjectId, companyName, clientType). Klienti = Desktop/WebClient.

Jméno k GUID se doplní přes BC „Telemetry User ID" → BC Users OData → dbo.BCUser → záložka 👤 Uživatelé.

B · Audit změn

BC Change Log (Page 405) → OData

Pole: Entry_No, Date_and_Time, User_ID (reálné jméno), Table_No/Caption, Field_No/Caption, Type_of_Change, Old/New_Value, Primary_Key.

Entry_No je per-firma sekvence → watermark + dedup per firma.

C · Permission errors

Log Analytics → AppTraces (RT0031)

Záznamy o chybějícím oprávnění. Vznikají typicky až po zúžení práv → slouží jako kontrola po nasazení permission setů.

6 · Datová vrstva & servisní účet

  • SQL BC_Telemetry co-located na serveru 10.8.2.225 (SQL Server 2022, DEFAULT instance). Schéma: raw tabulky → inkrementální rollup → agregáty + vw_Dash* pohledy.
  • Importy se připojují přes Integrated Security jako svc-bc-telemetry (db_datareader + db_datawriter + EXECUTE na ETL procy). Web na SQL nesahá.
  • Snapshot (Export-DashboardSnapshot.ps1) čte jen agregáty → data.json (malý i nad miliony raw řádků) → dashboard.

  • Stav spojení s BC — každé sezení proti BC API zapíše výsledek do ops/bc-status.json; dashboard jen čte tenhle soubor, takže indikátor nestojí žádné volání navíc.

A guide to working with the dashboard. It shows what people actually use in Business Central, who created, changed or deleted what and who is missing a permission after their rights were narrowed — the raw material for building tailored permission sets instead of blanket SUPER.

1 · Finding your way around

  • Header — the title on the left (click = back to the start), the BC connection indicator (green = we reached the BC tenant recently; hover for details), a live clock (a heartbeat proving the page is alive — if it stops, the page froze → Ctrl+F5), data age (how long ago the last import ran), the CS/EN language switch and the 🌙 / ☀ light/dark toggle.
  • KPI tiles — headline numbers (active users over 30 days, pages used, page opens, RT0031 errors). They are clickable — a click jumps to the matching tab.
  • Strip below the KPIs (synchronisation) — how many records exist in the cloud vs. how many were downloaded into the database (per module) + local database size.
  • 📊 Management report (top right) — opens an overview report with charts, running totals and rankings (top users/pages/companies, trend, audit) that can be printed, saved as PDF or downloaded as HTML.

2 · Tabs — what lives where

User activity

Who opens which BC pages and how often. The basis for designing roles — you see real usage. Filter by user/company, sort by "Opens", export.

👤 Users

Usage telemetry only knows users as a pseudonymous GUID. Here you map a real name to it (using the companies/pages shown as a hint); the name then appears everywhere. Fill in "Real name" → Save names.

Change audit

Who created/changed/deleted what and when — with the real name, company, table/field and old→new value. The Company and Action filters are drop-downs, dates are a from–to range.

Permission errors (RT0031)

Who is missing a permission. Watch this mainly for the first 2 weeks after narrowing rights — it tells you exactly what to grant.

Trend

Page opens and active users over time, with an optional per-company view (chart + table).

🗄 Database

SQL Server status, database size and the table list with row counts — the operational view.

🖥 Terminal

Live service activity and the log of the last import (auto-refresh every 10 s) — for when you want to see what the system is doing right now.

⚙ Audit settings

Pick the companies tracked by the change audit (switch off the huge ones) and delete already imported audit records.

⚙ Settings

BC connection check, manual data refresh, retention policy, import schedule, network whitelist, service restart, log maintenance.

3 · Main task: building tailored permissions

How to turn dashboard data into a permission set per user/role instead of blanket SUPER:

  1. Collect data — the user works with full access while data accumulates (ideally ~3 months).
  2. Map the names — the 👤 Users tab → add real names to the GUIDs and save.
  3. Narrow the selection — the User activity tab → filter by user / company, sort by "Opens".
  4. Export — ⬇ Export ▾ → pick CSV / TXT / HTML / PDF (CSV opens in Excel, separator ;, with real names). The entire filtered set is exported, not just the visible page.
  5. Analyse — a pivot table in Excel (rows = Page ID/Page, filter = user) gives the list of objects the user really touches.
  6. Deploy — build a permission set in BC from that, then remove full access.
  7. Verify — watch the Permission errors (RT0031) tab and grant whatever is missing.

Usage telemetry (Activity) only carries a pseudonym — which is why step 2 (name mapping) matters. The change audit carries the real name natively.

4 · Working with tables

  • Search — the field at the top filters across all columns ("contains").
  • Per-column filters — the row under the header: Company/Action = drop-down, text = "contains", date = a from–to range. "Clear filters" resets everything.
  • Sorting — click a column header (a second click reverses the direction).
  • Paging — at the bottom: « ‹ page X/Y › » plus a 50 / 100 / 200 / 500 / all selector. The default row count is set in ⚙ Settings (stored in the browser).
  • ⬇ Export ▾ — downloads the currently filtered and sorted rows as CSV (Excel, separator ;), TXT (tab), HTML (standalone table) or PDF (via print).

5 · Operations (⚙ Settings)

  • Business Central connection — shows whether we are really connected to the BC tenant, when that was last proven, and lets you request a fresh live check.
  • Manual data refresh — forces an immediate import + snapshot (otherwise it runs on schedule).
  • Import schedule — the "From–To" window, frequency (every N minutes) and weekdays.
  • Retention policy — how many months/days data is kept.
  • Network whitelist — which IP addresses may view the dashboard (single IP / CIDR / range).
  • Restart service — a safe self-service restart (after deploying server changes).

6 · Tips & troubleshooting

  • The dashboard will not load / "site cannot be reached" (timeout) — usually the firewall on the server (the dashboard rule does not apply to the currently active network profile after a reboot). An administrator fixes this on the server; afterwards Ctrl+F5 is enough.
  • The BC indicator is red or amber — amber means no successful contact with the tenant for over 26 hours (a missed nightly run); red means the last attempt failed and the tooltip gives the reason (expired secret, missing consent, revoked permissions).
  • The data looks old — check "data age" in the header; a manual refresh is in ⚙ Settings → Manual data refresh.
  • The live clock has stopped — the page froze, reload with Ctrl+F5.
  • Dark / light mode — the 🌙/☀ toggle in the header (the choice is remembered).
  • Language — the CS/EN switch in the header; it also switches this documentation and is remembered in the browser.
  • Print / PDF — the 🖨 button at the top of this tab prints the guide you are currently viewing, always on white. Choose "Save as PDF" in the dialog.

1 · Overview — what it is for

On top of Microsoft Dynamics 365 Business Central (Cloud / SaaS) it builds a system that answers three questions BC SaaS does not answer directly:

Module A

What users actually use

Page usage telemetry → the input for permission set mining (cutting rights down to what is genuinely needed instead of blanket SUPER).

Module B

Who created / changed / deleted what

Change audit from the BC Change Log with the user's real name (who, when, which table/field, old→new value).

Module C

Who is missing a permission

RT0031 permission errors from telemetry — catches users left without access after roles were deployed.

The architecture deliberately sits on the free tier (Application Insights, 5 GB/month free) + on-prem SQL + a lightweight Node dashboard → running costs are effectively zero and the data stays inside the domain.

2 · Architecture — data flow

BC Cloud ──telemetry──▶ Azure Application Insights / Log Analytics │ (Service Principal, non-interactive) ┌─────────────────────┼─────────────────────┐ module A module C module B (BC Change Log → OData) (AppPageViews) (AppTraces) └─────────────────────┼─────────────────────┘ ▼ SQL (raw → incremental rollup → aggregates) ← service account, via the daily task ▼ data.json ──▶ Node service (dashboard + IP whitelist) ← the web NEVER touches SQL/BC

Two separate identities, following least privilege:

  • Web service BC_Telemetry_Web (Node + NSSM, runs as LocalSystem) — serves the dashboard and never touches SQL or BC directly. Requests from the UI (import, purge, schedule…) are written as files into the ops/ queue.
  • Service account AXINETWORK\svc-bc-telemetry — runs the daily task BC_Telemetry_Daily (wrapper), the only thing that reaches SQL and BC OData and drains the ops queue.

This split is also why the BC connection check is performed by the service account and not by the web service: the service principal's secret lives in the service account's Credential Manager, which LocalSystem cannot read.

3 · Registration with Microsoft (Azure + Entra)

One Microsoft Entra ID application handles non-interactive (server-to-server) reading of both telemetry and the BC API — app registration BC_Telemetry_SP (service principal).

3.1 Azure subscription + Application Insights (modules A/C)

  1. Azure Portal → Subscriptions → Pay-as-you-go (App Insights runs on the free tier = $0; the card is only there for the identity).
  2. Resource group rg-bc-telemetry, region West Europe.
  3. Application Insights appinsights-bc-production, Resource Mode: Workspace-based (creates a Log Analytics workspace).
  4. Workspace → Usage and estimated costs → Data retention 31 days + daily cap 0.5 GB/day (a cost fuse).
  5. Workspace → Overview → copy the Workspace ID (into the A/C import scripts).
  6. App Insights → Overview → copy the connection string (pasted into BC, see §4).

3.2 Entra app registration (service principal)

  1. Entra → App registrations → New registration → BC_Telemetry_SP, single tenant → Register.
  2. Copy the Application (client) ID (NOT the "Object ID" — that is something else).
  3. Certificates & secrets → New client secret → copy the Value (shown only once).

⚠ Trap: the secret is the Value (~40 characters, mzm8Q~…), NOT the Secret ID (a 36-character GUID) — mixing them up makes the token request return 401. The secret is never written down; it lives in the service account's Credential Manager (targets BC_Telemetry_SP and BC_Telemetry_BCAPI). Current expiry 2028-06-07 — keep an eye on it.

3.3 Authorisation for App Insights (modules A/C)

Log Analytics workspace → Access control (IAM) → Add role assignment → Log Analytics Reader → member BC_Telemetry_SP → Review + assign. That lets the SP read AppPageViews / AppTraces through KQL.

3.4 Authorisation for the BC API (module B, S2S) — three traps

  1. Redirect URI — App registration → Authentication → Add a platform → Web → https://businesscentral.dynamics.com/OAuthLanding.htm (do NOT tick implicit grant).
    Without it, "Grant consent" in BC fails with AADSTS500113.
  2. API permission + admin consent — API permissions → Add → APIs my organization uses → Dynamics 365 Business Central → Application permissions → API.ReadWrite.All → Add → Grant admin consent (must be a green Granted).
    Without it the token has empty roles → 401 even with BC permission sets in place.
  3. Registering the app user inside BC — see §4.3.

4 · Registration in Business Central

4.1 Turn telemetry on

BC Admin Center (…/<tenant>/admin) → Environments → Production → Telemetry → Define → paste the connection string from App Insights → Save. In current BC versions no environment restart is needed; data starts flowing within ~5 minutes of real user activity (Desktop / WebClient).

4.2 Change Log + web service (module B)

  1. Change Log Setup → Change Log Activated = ON.
  2. Tables → enable Log Insertion / Modification / Deletion for sensitive tables (e.g. Access Control 2000000053, User 2000000120, documents, items). It does not log retroactively.
  3. Web Services → New → type Page, object ID 405, service name ChangelogEntry, Published.

⚠ Microsoft is gradually retiring the publishing of UI pages as web services → the durable variant is a custom AL API page (planned). Note that moving to the standard /api/v2.0 is not an option here: neither Change Log Entry nor BC Users exist as entities in API v2.0.

4.3 App user for the service principal (S2S)

  1. BC web client → search for "Microsoft Entra Applications" (page 9861) → New.
  2. Client ID = the application (client) ID from §3.2 + a description.
  3. Permission sets → add D365 BUS PREMIUM (or a custom read-only set).
  4. Company — leave empty = applies to all companies.
  5. State → Enabled → Grant consent (sign in as an admin) → the user ID is filled in. OData then reads all 12 companies.

⚠ SUPER and SUPER (DATA) cannot be assigned to an app user — BC rejects them. Use the D365 sets or a custom read-only set.

5 · Three modules — what they read

A · Page usage

Log Analytics → AppPageViews

Identity = UserId = a pseudonymous GUID (NOT the AAD object id; Microsoft does not resolve it). BC dimensions live in Properties.* (alObjectId, companyName, clientType). Clients = Desktop/WebClient.

The name behind a GUID is filled in via BC "Telemetry User ID" → BC Users OData → dbo.BCUser → the 👤 Users tab.

B · Change audit

BC Change Log (page 405) → OData

Fields: Entry_No, Date_and_Time, User_ID (real name), Table_No/Caption, Field_No/Caption, Type_of_Change, Old/New_Value, Primary_Key.

Entry_No is a per-company sequence → watermark + dedup per company.

C · Permission errors

Log Analytics → AppTraces (RT0031)

Records of missing permissions. They typically appear only after rights are narrowed → they act as the verification step after permission sets are deployed.

6 · Data layer & service account

  • SQL BC_Telemetry co-located on server 10.8.2.225 (SQL Server 2022, default instance). Schema: raw tables → incremental rollup → aggregates + vw_Dash* views.
  • Imports connect with integrated security as svc-bc-telemetry (db_datareader + db_datawriter + EXECUTE on the ETL procs). The web never touches SQL.
  • Snapshot (Export-DashboardSnapshot.ps1) reads aggregates only → data.json (small even on millions of raw rows) → dashboard.
  • Ops queue — the web (LocalSystem) writes a request into ops/ and the daily task (svc) executes it. That is how import / audit purge / schedule / restart work without the web having any rights on SQL or BC.
  • BC connection status — every BC API session writes its result into ops/bc-status.json; the dashboard only reads that file, so the indicator costs no extra BC calls.
  • Import schedule is driven by the wrapper (an OS task once at startTime, then a loop every intervalMinutes within the window on the selected days) — the OS task trigger cannot be changed from LocalSystem without the svc password.
